# 화면과 대화로 사용하는 공동 업무 앱

비개발자가 자신의 업무를 설명하면 에이전트가 설계·도구 준비·구현·검증을 맡는다. 목표는 실제로 동료와 쓰는 앱을 만들고, 참여자가 자료의 이동·저장·공유 범위를 이해하며 기능을 계속 개선할 수 있게 하는 것이다. 기술 용어는 업무에서 하는 역할로 풀어 설명한다.

## 이 과정의 핵심 선택

- **사람에게 두 가지 사용 방법을 제공한다.** 웹의 입력창·버튼·목록을 직접 조작하거나, 에이전트에게 자연어로 업무를 요청하고 결과를 받는다. 에이전트는 업무용 MCP를 통해 서버를 사용한다.
- **두 경로가 같은 업무 데이터와 서버 규칙을 사용한다.** Supabase로 로그인·저장·접근 권한의 기반을 마련하며, 에이전트도 사용자가 허용한 범위에서 작업한다.
- **동료가 자기 계정으로 접속하는 공동 서비스를 배포한다.** 웹과 에이전트의 실제 사용까지 스킬의 목표에 포함한다.

예를 들어 화면에서 요청을 등록한 뒤 에이전트에게 “내가 볼 수 있는 미처리 요청을 알려줘”라고 물을 수 있다. 변경을 허용한 업무라면 “이 요청을 완료로 바꿔줘”라고 말하고 웹에서 결과를 확인한다. 제공할 업무 범위는 참여자와 정하며, 모든 화면 조작을 MCP 도구와 일대일로 대응시킬 필요는 없다.

## 진행을 이끄는 원칙

**업무에서 시작한다.** 최근 실제 사례를 바탕으로 누가 어떤 자료를 다루고 어떤 결과가 필요한지 알아본다. 웹에서 할 행동과 에이전트에게 할 말, 공유·수정 범위를 함께 정한다. 개발 방식이 고민이라면 개인 자동화·공동 서비스, 사용 인터페이스, 인증·권한, 자료 확보 방법을 비교해 준다.

**그림으로 함께 설계한다.** 인터뷰 내용을 바탕으로 구성 요소와 데이터 흐름을 살펴볼 수 있는 HTML을 만든다. 대표 업무부터 보여주며 참여자가 잘못 이해된 부분을 고칠 수 있게 한다. 계획과 확인된 구현을 구별하고, 흐름이 바뀌면 그림도 갱신한다.

**에이전트가 실행을 맡는다.** 필요한 CLI와 도구를 직접 준비하고 사용한다. 사람의 개입은 본인 인증이나 중요한 업무·비용 결정처럼 필요한 지점에 집중한다. 개발용 관리 도구와 완성된 앱을 쓰는 에이전트의 MCP 연결은 역할이 다르다.

**작은 업무 하나를 끝까지 연결한다.** 데이터·권한·서버·웹·MCP를 함께 다루며 사용 가능한 결과를 만든다. 실제 사용할 에이전트의 연결 가능성은 초기에 확인한다. 기능을 바꿀 때 기존 구조를 재사용하고, 대체된 코드와 중복 규칙을 정리하는 일도 작업에 포함한다.

**PRD·ADR·티켓으로 이어간다.** PRD에는 업무 목표와 범위, ADR에는 중요한 설계 선택과 이유, 티켓에는 작업과 완료 근거를 남긴다. 작성과 갱신은 에이전트가 맡는다. 기록의 깊이는 변경 규모에 맞추되 다음 세션에서도 결정과 남은 일을 찾을 수 있게 한다.

## 상황에 맞춰 사용하기

새 앱은 업무 인터뷰부터 시작하고, 기존 앱은 문서와 구현을 확인해 필요한 작업부터 이어간다. 질문 수와 단계 순서는 상황에 맞게 정한다. 설명·설계·구현 중 사용자가 요청한 범위에서 진행하며, 스킬 편집 요청은 이 가이드 자체에 적용한다. 실제 앱 작업은 참여자의 앱 폴더에서 수행한다.

## 성공을 판단하는 기준

실제 업무가 웹 조작과 에이전트의 자연어 요청으로 처리되고, 동료의 계정에서도 허용된 작업이 가능해야 한다. 도구 직접 호출 검사와 사람이 에이전트에게 요청하는 경험은 각각 확인한다. 로컬 구현·배포·실사용 중 어디까지 확인했는지와 남은 조건을 전한다.

참여자의 이해는 대화나 사용 중 드러난 피드백으로 판단한다. 스킬 자체를 평가할 때는 대표 업무의 시작·변경·재개를 통해 에이전트가 실행을 맡는지, 참여자가 흐름을 이해하는지, 구조와 기록을 유지하는지 살펴본다. 문서 점검과 실제 사용 관찰의 결과는 구별한다.
