# PRD·ADR·티켓으로 운영하기

문서는 에이전트가 작성·갱신하고 참여자는 업무 내용과 중요한 선택을 판단한다. 목적은 요구와 결정의 이유를 유지하고, 다음 작업을 쉽게 이어가는 것이다.

| 기록 | 맡는 역할 | 신규 앱의 위치 예시 |
| --- | --- | --- |
| PRD | 누구의 어떤 문제를 어디까지 해결하는가 | `docs/prd.md` |
| ADR | 중요한 설계 선택을 왜 했는가 | `docs/adr/0001-설명.md` |
| 티켓 | 이번에 무엇을 바꾸며 무엇으로 완료를 확인하는가 | `docs/tickets/T001-설명.md` |
| 시작 문서 | 현재 기준과 진행 작업을 찾는 색인 | `docs/START-HERE.md` |

기존 프로젝트의 문서나 작업 도구가 같은 역할을 맡고 있다면 활용한다. 새 프로젝트도 첫 업무에 필요한 짧은 기록부터 시작한다. 파일 위치와 양식은 예시이며, 같은 내용을 여러 곳에서 따로 관리하기보다 링크로 연결한다.

## 기록의 연결

인터뷰에서 정한 업무를 PRD 시나리오로 정리하고, 설계 선택은 ADR에 연결한다. 이를 구현하는 티켓에 범위와 수용 기준을 적고 코드·검증 결과·흐름도를 연결한다. 일관된 식별자가 있으면 추적하기 쉽다.

예: `S01 팀 요청 처리` → `ADR 0001 웹과 MCP의 공통 권한·저장 규칙` → `T001 등록·조회·상태 변경 구현`.

PRD에는 같은 업무를 웹에서 수행하는 행동과 에이전트에게 자연어로 요청하는 예시·기대 결과를 함께 담는다. 티켓은 가능한 한 사용자가 끝까지 해볼 수 있는 작은 업무 단위로 잡는다.

## 변경과 재개

제품 범위가 바뀌면 PRD를, 중요한 설계 선택이 바뀌면 ADR을 갱신한다. 채택한 결정을 바꿀 때는 이유와 대체 관계를 남긴다. 통상적인 구현·오류 수정·구조 정리는 티켓으로 관리한다.

티켓은 구현과 필요한 정리·검증을 마쳤을 때 완료한다. 배포나 실사용이 남았다면 후속 작업을 연결한다. 현재 상태, 미해결 결정, 다음 작업은 시작 문서에서 찾을 수 있게 한다. 재개할 때 관련 문서와 실제 코드를 함께 확인하고, 충돌이 있으면 의도와 현재 동작을 구별해 해결한다.

## 짧은 작성 예시

필요한 항목을 골라 프로젝트 규모에 맞춰 사용한다.

- **PRD:** 업무 문제와 사용자 / 시나리오와 두 사용 경로 / 공유·편집 범위 / 성공 조건 / 이번에 제외할 것.
- **ADR:** 배경 / 검토한 대안 / 결정과 이유 / 영향 / 채택 상태와 대체 관계.
- **티켓:** 연결된 시나리오·ADR / 바꿀 범위 / 완료 조건 / 재사용·정리할 부분 / 실제 검사 결과와 남은 일.

문서의 길이보다 참여자의 업무 의도, 구현, 검증이 서로 맞는지가 중요하다.
