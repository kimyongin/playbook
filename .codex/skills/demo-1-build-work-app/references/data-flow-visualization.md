# 인터뷰에서 데이터 흐름 HTML로

참여자가 업무를 설명하면 에이전트가 구성 요소와 데이터 이동을 정리해 독립적으로 열 수 있는 인터랙티브 HTML로 보여준다. 데모 설계의 일부로 진행하며, 첫 대표 업무를 설명할 수 있을 때 초안을 만들고 피드백으로 다듬는다.

## 인터뷰의 초점

기존 대화에서 알려진 내용을 활용하고 업무 의미가 불명확한 부분을 묻는다. 예를 들어 “웹에서 무엇을 누르나요?”, “에이전트에게는 어떻게 말하고 싶나요?”, “어떤 자료가 남고 누가 보거나 고칠 수 있나요?”가 설계의 출발점이다.

그림에는 웹·에이전트·서버·DB·외부 서비스·로그인 제공자 중 실제로 필요한 요소를 담는다. 각 요소가 맡는 일과 보관하는 자료, 연결마다 보내는 정보와 돌아오는 결과, 권한을 검사하는 위치가 보이면 된다. 대표적인 실패가 업무에 영향을 준다면 그 결과도 설명한다.

웹 사용은 **사람의 화면 조작 → 요청 → 처리·저장 → 화면 결과**, 에이전트 사용은 **사람의 자연어 요청 → 에이전트의 도구 호출 → 처리·조회 → 사람에게 설명**으로 비교할 수 있다. 자연어 대화와 MCP 도구 입력은 구별하고, 실제로 어떤 정보가 서버에 전달되는지 표현한다.

## 그림의 정확성

계획·현재 구현·미확인 부분과 대상 환경을 표시한다. 코드에서 확인한 구조를 운영에서 검증한 결과로 표현하지 않는다. Supabase의 Data API/RPC를 직접 쓰는지 서버 함수를 거치는지 등은 실제 설계와 구현을 따른다.

사용자의 로그인과 에이전트 연결 동의는 각각 보여준다. 비밀번호가 앱 서버로 전달되는 것처럼 그리거나 개발용 CLI를 이용자의 업무 경로에 섞지 않는다. 역할 하나가 반드시 별도 서버 한 대를 뜻하지는 않는다.

## HTML과 유지 관리

전체 관계와 대표 시나리오를 쉽게 오가며 자료의 이동을 살펴볼 수 있게 한다. 단계 이동, 요소 선택, 실패 흐름 등 상호작용은 설명에 도움이 되는 만큼 선택한다. 화면 크기와 접근성을 고려하되 구체적인 배치는 프로젝트에 맞게 설계한다.

HTML은 스타일·동작·예시 데이터를 포함해 네트워크 없이 열 수 있는 설명용 파일로 만든다. 실제 서비스 호출이나 비밀값은 포함하지 않고, 사용자 입력과 외부 자료는 실행되지 않는 텍스트로 다룬다. 가능한 환경에서 브라우저로 열어 읽기와 조작을 확인한 뒤 사용자에게 보여준다.

기본 저장 위치는 `docs/flows/project-flow.html`이며, 근거와 관련 PRD·ADR·티켓은 옆의 `project-flow.md`나 기존 설계 기록에 연결한다. 통신·저장·권한이 바뀌면 영향받는 그림을 함께 갱신한다. 사용자에게는 파일 링크와 먼저 볼 업무를 안내하고, 피드백으로 잘못 이해한 흐름을 수정한다.
